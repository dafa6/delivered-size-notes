Delivered Size Notes

The gap between what you ask a hosted image model for and what it hands back.

An API key, or a browser tab

Two ways to use a hosted image model: call the API yourself, or use an interface somebody else built on top of it. Most write-ups assume the first and most tools assume the second, and the choice is usually made by whichever page you happened to land on rather than by what you are doing.

Here is the version I would give someone who asked, including the cases where the API is obviously right.

Use the API when any of these are true

The output feeds a system, not a person. If images are generated on a schedule, in response to user actions, or as part of a pipeline, you need programmatic access. Nothing else is a real option.

You need the parameters an interface does not expose. Seeds where available, unusual sizes, response formats, streaming, moderation settings. Wrappers pick defaults, and a good wrapper picks good ones, but picked is picked.

Volume makes the margin matter. Any interface built on top of an API has to cover its own costs. At low volume the difference is noise. At high volume it is the whole conversation, and you should be running the arithmetic rather than reading a pricing page.

Data handling is a compliance question. Fewer parties is simpler to reason about. If you have to document where a file went, one hop beats two.

Use someone else's interface when any of these are true

You are evaluating, not shipping. The question "is this model good enough for my job" does not need a key, a billing account, or a client library. It needs ten minutes and a few real prompts. Standing up an integration to answer it is a large fixed cost against a question that might be answered "no".

The gate in front of the API is nontrivial. Some model tiers sit behind organisation-level verification. If you cannot get through that this week, an interface that already has access is the difference between trying the model and not.

You want a comparison, not a generation. Running the same prompt through two model variants side by side is ordinary in an interface and a small scripting job through the API.

The interface does something the API does not. This is the only genuinely interesting case. An API returns an image. A well-built interface can enforce a discipline the API cannot: recomputing edits from your original rather than chaining them, printing which model actually answered, resolving aspect ratios against a published table instead of letting you guess. Those are product decisions, not model capabilities, and you do not get them by calling the endpoint yourself — you get them by building them, which is the thing you were trying to avoid.

The question that usually settles it

Is this a one-off, or is it going to run again?

One-off, or fewer than a few dozen images, or you do not yet know whether the model is right: use an interface. The setup cost of the API is real and the marginal saving is not.

Running repeatedly, or embedded in something: use the API. You will need the control eventually and migrating later is more work than starting there.

What to check before trusting either

The same three things, in both cases:

  • What does one image cost you, at your actual configuration, measured rather than estimated.
  • What happens to a failed or blocked request — billed or not.
  • What gets recorded, so that in three months you can answer why an image looks the way it does.

An interface that cannot answer the first two is asking for more trust than it has earned. An API integration that does not record the third is going to produce an unanswerable question later.

For the evaluation case specifically, a browser interface that runs the first image free, no card removes the setup cost entirely, and the measured per-image figures at each tier are at gptimage25.top/pricing with the upstream cost next to the retail price — which is also the number you need to decide whether to go direct.
