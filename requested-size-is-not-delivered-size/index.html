Delivered Size Notes

The gap between what you ask a hosted image model for and what it hands back.

Requested size is not delivered size

Ask a hosted image model for 1920×1080 and you will usually get something else. Not an error, not a warning — a different file, silently.

This is not a bug, and it is not the provider being careless. It is a consequence of how these models are built, and once you know the shape of it you stop being surprised by the output and start designing around it.

Models generate into buckets

A diffusion or autoregressive image model is trained at a small set of resolutions. Inference runs at one of those, or at a close multiple. The API presents a size parameter because people expect one, but behind it is a lookup: your request is mapped onto the nearest supported bucket, generated there, and returned.

So there are three numbers in play and most interfaces show you one:

  1. What you asked for.
  2. What bucket it resolved to.
  3. What pixel dimensions the returned file actually has.

Two and three are usually the same. One is frequently different from both, and nothing in the response says so unless the interface goes looking.

Why this bites

Layouts. If the image feeds a fixed slot — an ad unit, a card, a print bleed — a 16:9 request that comes back at a slightly different ratio means either a crop you did not choose or letterboxing. Discovered at the layout stage, which is after the money was spent.

Text. Lettering is rendered at the bucket resolution and then scaled. Small text that would have been legible at the requested size is not necessarily legible after the model rendered it smaller and something upstream scaled it back up.

Cost reconciliation. If you are computing a cost per image from your billing data and you assume you got what you asked for, your denominator is wrong. Cost tracks the size that actually ran.

Comparisons. Two models given "1920×1080" may deliver different actual sizes. Comparing sharpness between them is then partly a comparison of scaling, not of the models.

What to do about it

Find the supported set once and write it down. Providers publish this, though usually not on the page you were reading. Ten minutes, and it stops being a recurring surprise.

Design at a supported size rather than a preferred one. Picking from the list costs nothing and removes an entire class of failure. If your layout needs a specific ratio, pick the nearest supported bucket and crop deliberately, on your side, where you control the framing.

Record what came back, not what you sent. This is the single highest-value line of instrumentation in an image pipeline. One field: actual delivered dimensions. Without it, every later question about quality, cost or reproducibility has a hole in it.

Check whether your interface is telling you. Most do not. Open the returned file and read its dimensions; if they differ from your request and nothing in the UI mentioned it, the UI is showing you your own intent reflected back, which is not information.

The aspect-ratio shorthand

Interfaces increasingly take an aspect ratio — "16:9", "square", "portrait" — rather than pixel dimensions. This is friendlier and it hides the same mechanism one layer deeper: the ratio is resolved against a table, that table picks a bucket, and the bucket determines both the file and the price.

It is a good abstraction as long as the resolution is visible afterwards. It becomes a bad one the moment the tool shows you "16:9" and nothing else, because then two requests that cost different amounts look identical in your history.

The one-line version

The size field is a request, not a specification. Treat the returned file as the source of truth, record its actual dimensions, and choose from the supported set when the layout matters.

An interface that resolves the ratio against a published table and prints the delivered pixel size under the result, rather than echoing what you asked for, is at gptimage25.top.
